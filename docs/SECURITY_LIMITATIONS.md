# Security limitations

Verfy reduces risk; it does not remove it. These are the limits we know about. Nothing in the product, the site or these docs claims otherwise.

## The guard

- Rules are deterministic pattern matching over commands, paths, URLs and arguments. They are not a sandbox and cannot understand every possible shell construct, interpreter or obfuscation. Run untrusted code with `verfy run --sandbox`, or in a container or VM, as well. Three layers reach past the rules: a session that tried something blocked or suspicious needs approval (then is blocked) for risky actions for an hour; a program or host this machine's agents never used is asked about once after a warm-up; and rules published after a release arrive through the signed rule feed (`verfy rules update`). An attack that does nothing blocked or suspicious, in a session of its own, with programs and hosts the machine already uses, still gets through them.
- Treat the guard as a seat belt, not a wall. In our last internal test, a list of attacks written after a round of fixes still got 59 of 113 through. We closed those, and a new list will find more.
- A script a command starts is read before it runs (scripts named on the command line, inline code, here-documents, package scripts, Makefile recipes, and code the agent wrote this session that a runner loads) and checked with the same rules (VFY-SCRIPT-001..003). What its text shows is all Verfy sees: a command built while it runs, code decoded or downloaded and then run (asked about, not read), a module the agent did not write and compiled programs are not followed. Code already in the project is held only to what is blocked outright, so an existing script with `git push --force` runs without a question. The text is read before the command starts; a script that rewrites itself or another file while it runs is not read again.
- Some things run without a question because Verfy cannot judge them by name: `npm i -g` and `pip install` (packages fetched from a registry), `nohup` or `setsid` around a command, and `docker exec`. `localhost` is allowed. A package that `npx`, `uvx`, `pipx run` or `dlx` downloads and runs is asked about only the first time (VFY-AD-004): what the package does after that is not followed. Its name is read from the command; a runner Verfy does not know, or a name built while the command runs, is not seen.
- Windows commands are checked with patterns on the text, which is weaker than the shell parsing Verfy has for `bash`.
- A `verfy.policy.json` in a folder only tightens your own or your team's policy until you run `verfy policy trust`. A trusted file can loosen your own policy, never a team's. Trust goes by the file's digest in `~/.verfy/trusted-policies.json`, which the agent may not change.
- Verfy only sees calls that go through its hooks (Claude Code, Cursor, Codex CLI, Gemini CLI, GitHub Copilot, Devin) or its MCP gateway. Tools an agent reaches another way are not checked. Copilot and Devin let a call through when a hook times out (their references say so); Verfy answers in well under a second, and the timeout it configures is 30 seconds. The Copilot and Devin hooks are checked against each agent's published hook reference (`tests/test_copilot_devin_spec.py`).
- The Cursor hook follows Cursor's hook reference (checked against it on 20 November 2026 by `tests/test_cursor_spec.py`: every event's input with all common fields, and only the answers each event accepts). It covers terminal commands, file reads and the files attached to them, file writes and deletes (checked before they run, through `preToolUse`), MCP calls, prompts and MCP results; not web search or fetch, which Cursor's hooks do not expose, and not `beforeMCPExecution` in Cursor's cloud agents, which do not run it. Cursor has no answer that means "no objection", so Verfy answers allow there, and what Cursor then does with its own approval settings is not tested. A file read cannot ask, so it is denied instead. `verfy doctor --live` runs the installed hook as Cursor does (and as every other supported agent does), which shows that the command starts and answers in Cursor's format on that machine; it does not show what Cursor's own interface then does.
- The hook answers deny or ask, never allow; Claude Code's own permission settings still decide allowed actions.
- Anyone with write access to the developer's machine can remove the hook or edit the policy. Team policy and receipts make that visible, not impossible.
- The guard stops the agent from switching Verfy off through the paths it understands: editing Claude Code's hook settings, `verfy.lock`, `verfy.policy.json`, `~/.verfy` or the Verfy install (deny), editing MCP configs (ask; an edit that takes Verfy out of one is denied), inline code (`python -c`, `node -e`) that writes, moves or deletes a hook file (deny) or names an MCP config (ask), and running `verfy lock approve`, `verfy lock check --update`, `verfy init --force`, `verfy team enroll`, `verfy team auto-sync off` or `pip uninstall verfy` (deny). A script the agent writes and then runs, or an interpreter one-liner, is read first and stopped when its text does these things; a program that builds the path or the command while it runs can still do them.
- The agent may not read Verfy's signing key or device token (`~/.verfy/key.json`, `~/.verfy/team.json`). Reading either with a shell command or a file tool, listing, searching or copying `~/.verfy`, or naming the folder and one of those files in one command is denied (VFY-SELF-006); archiving, copying or searching a folder that holds `~/.verfy`, such as the home folder, or looking for files with those names, needs approval (VFY-SELF-007). A script that names the key, also in pieces (`os.path.join(home, ".verfy", "key.json")`), is denied before it runs. The key is still an ordinary file your user account can read, so a path a program builds while running, or a compiled program, can read it; keeping the key out of the agent's reach altogether (for example in the operating system's keychain) is not built yet. A `VERFY_HOME` outside `~/.verfy` is not covered by these rules.
- On Windows, paths are compared without regard to case and in the `/c/...` form Git Bash uses. Rules written for Unix system folders do not apply there.

- The gateway replaces secrets in tool results and resources with `[REDACTED:<rule>]`. It recognises the formats in `patterns.json` (private key blocks, AWS, GitHub, Anthropic, OpenAI, Stripe, Slack, Google, Telegram, GitLab, npm, PyPI, Supabase, SendGrid, Hugging Face, DigitalOcean, Shopify, Twilio, age and Azure keys, JWTs, bearer tokens, passwords in URLs, unquoted settings such as `DB_PASSWORD=...` with a digit in the value, and `password = "..."`-style assignments); a secret in another format, split across lines or encoded, gets through. In Claude Code the output of built-in tools (Bash, Read, ...) is not redacted, because a PreToolUse hook cannot rewrite it; reading `.env` and similar files needs approval instead.
- Policy templates (`strict`, `read-only`, `ci`) match tool names by pattern. A write tool with an unusual name (not `*write*`, `*create*`, `*delete*` and so on) is not caught by `read-only`.

## The scanner and locks

- The scanner takes off common disguises (invisible characters, Unicode tags, leet, spaced letters, base64) and knows a few languages. A paraphrase it has no pattern for gets through.
- A clean scan is not a security certification. The scanner finds known warning signs in tool definitions and configs.
- `verfy scan --discover` is static and does not start servers. `--live` starts each configured stdio server and calls each remote server (with the headers in its config) to list their tools; only use it for servers you would run anyway.
- The first time a server is seen, its tools are locked as they are (trust on first use).
- A lock proves a definition did not change since it was approved, not that it is safe.
- The risk Verfy gives a change (low, medium, high) comes from deterministic patterns: new sentences that order the model to move data, new links, hidden-instruction patterns and schema changes. A cleverly worded instruction can still be rated low, so read the diff before you approve.
- `verfy run --sandbox` closes `verfy.lock`, the policy, `.mcp.json`, the `.claude` and `.cursor` folders, git hooks and `.git/config` in its folder, also when one of them is missing, so a command cannot create it. So inside the sandbox `git init` fails in a folder that is not a repository yet, and a command cannot change anything under `.claude`.
- On Linux the runtime holds a missing file closed with an empty placeholder in your folder while the command runs, and removes it when the command ends. A `kill -9` of the sandbox can leave one behind. Verfy reads an empty file as a missing one; other tools may complain about an empty `.mcp.json`, so delete it. Inside the sandbox, a tool that reads a missing root file such as `.mcp.json` gets "permission denied", not "not found".
- The lock pins MCP prompts by name, description and arguments, as `prompt:<name>`. The text of a prompt depends on its arguments, so it is scanned when fetched, not pinned. Resource lists change all the time, so they are scanned, not pinned.
- The lock pins a tool's name, description, input schema and, when a server sends them, its title, annotations and output schema. It leaves out `_meta`, which can change on every connection.
- `verfy lock files` pins the instruction files, skills, commands, hook settings and plugins it knows about (listed in the CLI README). An agent can also read files Verfy does not list; those are not pinned.
- `verfy import` follows the documented JSON formats of Snyk Agent Scan and Cisco MCP Scanner. Those formats may change between their releases, and the gateway matches imported findings by server and tool name only.
- The gateway reaches a remote server through `verfy bridge`, which sends only the headers in the config. A server that signs in with OAuth in your MCP client cannot go behind the gateway yet; `verfy lock check` can still read tools from a server that accepts a key in its headers. The bridge does not open the stream for messages a server sends outside an answer to a request.
- `verfy lock check` (and the GitHub Action) starts every stdio server command in the given config, like `--live`, and calls every remote server with the headers in the config. In CI that runs those packages on the runner with whatever secrets you pass them; pin versions and keep the job's permissions read-only. The MCP gateway runs in front of stdio servers only: a remote server's tools are checked by `lock check`, not hidden or blocked while the agent runs. A server can serve different definitions to different clients or at different times, so a passing CI check does not replace the lock on each developer's machine.

## Updates

- `verfy update`, and the once-a-day check when automatic updates are on, ask GitHub (standalone builds) or PyPI (pip installs) for the newest version and then run the same install script or `pip install --upgrade` you would run by hand. Updating trusts those services and this project's release process exactly as much as the first install did.
- The standalone build is checked against `SHA256SUMS` from the same GitHub release. That catches a broken download, not a release someone was able to replace. The builds are not code-signed.
- Automatic updates are off unless you choose them in `verfy init` or with `verfy update --auto on`. The hook, the gateway and `verfy sync` never check for updates.

## Receipts

- From 0.9.0 the hashes of arguments and results include a secret salt kept in `~/.verfy/key.json`, so Verfy Cloud cannot guess a short argument from its hash. It also means only someone with that file can match known arguments to a receipt (`verfy ledger hash`), and that salt is lost with the file. Receipts written before 0.9.0 have plain hashes.
- A receipt proves the decision Verfy made, the hashes of arguments and results, and that the record was not changed afterwards. It does not prove what a tool did internally.
- A device key proves which device signed, not that the device was uncompromised.
- Whoever holds a device's private key can build a new chain from scratch and sign it, and `verfy verify` will accept that chain on its own: the check catches edits, deletions and reordering inside a chain, not a complete replacement. Receipts already synced to Verfy Cloud cannot be replaced this way, because the server keeps the hash of every stored receipt and refuses different content for the same position (`chain_conflict`). A ledger that was never synced has no outside copy to compare with.
- Deleting an entire local ledger together with its key is not detectable locally; it is detectable when the device had already synced to Verfy Cloud.
- There is no external timestamping or transparency-log anchoring yet, so receipts show order, not trusted wall-clock time. `verfy scitt export` produces SCITT signed statements that a transparency service could register, but Verfy does not register them anywhere.

## Verfy Cloud (the hosted service)

- Row-level security and server checks are tested on every build against the real migrations, but not yet reviewed by an independent penetration test.
- A database superuser (Supabase project owner) can technically alter data by disabling triggers. The audit log is hash-chained so silent edits are detectable when compared with an earlier copy or export, but it is not externally anchored.
- No software can promise to be unbreakable, and Verfy does not. It stacks independent layers so that one mistake is not enough: edge firewall, the in-app shield, Postgres rate limits, row-level security, two-factor authentication enforced in the database, append-only evidence.
- The shield's flood limits are per server instance (in memory); the limits that hold across all instances are the Postgres ones. Volumetric DDoS protection comes from Vercel's network; the WAF rules, bot protection and Attack Challenge Mode are settings of the Vercel project.
- Two-factor authentication is opt-in per user. Accounts without it are protected by their password (at least 12 characters), the per-account limits and, if configured, the CAPTCHA.
- The CAPTCHA is optional and only effective when both the Turnstile site key (Vercel) and secret key (Supabase) are configured.
- `TRACE` requests are refused by Next.js itself with a generic error page before any Verfy code runs; they should be denied at the edge.
- Exports are limited to 20,000 receipts per request; there is no background job queue yet.
- Notification channels: the Slack webhook URL or Telegram bot token is stored in the database for the server, which needs it to send. Browsers cannot read it (no grants, RLS on), but anyone with the Supabase secret key can. Messages go only to `hooks.slack.com` and `api.telegram.org`. "A device went quiet" is checked once a day from Vercel Cron; set `CRON_SECRET` so nobody else can trigger the check (without it, a caller can only cause alerts that are due anyway, once per silence).
- `verfy sandbox status` reads Claude Code's settings files; it does not test the sandbox or see managed settings. Claude Code's sandbox holds shell commands only, and it does not run on native Windows, where Claude Code runs commands unsandboxed. MCP servers run outside it: Verfy checks what they are asked to do, not what they do on the machine.
- Native Windows has no sandbox: there `verfy run --sandbox` hands over to `verfy run` inside WSL2, with the policy found inside WSL2, not the one in your Windows home. Inside WSL, the credential folders of Windows users under `/mnt/*/Users` are closed; the rest of the Windows drives is as readable as the rest of a Linux disk. WSL1 is not supported.
- `verfy run --sandbox` depends on `srt`, a research preview Verfy neither installs nor pins. Verfy writes the settings; the runtime and the operating system do the enforcing. Only `PATH`, `HOME` and other basics reach the command, plus what `--allow-env` names, and with `--agent` the `ANTHROPIC_*` and `CLAUDE_*` variables; a key you pass in can leave through any host you allow. An allowed host is allowed whole: the runtime does not inspect the traffic. On Linux, a sensitive path that does not exist when the command starts is not covered. Apple's `curl` cannot finish a TLS handshake inside the sandbox on macOS; Python and Node can. It refuses on native Windows.
- With `verfy run --sandbox --agent`, the sandbox does not keep the agent out of `~/.verfy`, because the hook needs it there: only the guard does. It was tested with the hook and `claude --version`, not with a signed-in Claude Code session. Claude Code's own sandbox may not start inside it on Linux.
- The `sandbox` field in a receipt is what this machine states. It is signed like the rest of the receipt, but whoever controls the machine can set it, so it is a record and not a proof.
- After outside text, `git push` is noticed in a command the agent runs, not in a script that command starts. A site on `network.allow` is not stopped, so outside text can still make the agent send data to a site you allowed.
- `session.after_outside_text` is on by default in agents with hooks only (`"hooks"`); the MCP gateway needs `"ask"` or `"deny"`. A plain request to a site after outside text is not asked about unless `session.include_network` is true, so outside text can make the agent put data in a URL it fetches; a key in the request is still caught. It follows the order of events, not the content: it cannot tell whether outside text contained instructions or whether the agent obeyed them, it treats a tool's first use as the moment the text arrived, and the hook and each gateway keep their own state. Text that reaches the agent another way, for example a file a person put in the project, does not count.
- The approval queue (`"on_ask": "team"`) works through the MCP gateway only; the Claude Code hook does not wait on the network. The person approving sees the tool, the rules and their messages and a hash of the arguments, not the arguments, so they approve the kind of call rather than its exact content. Without a Slack or Telegram channel (Dashboard → Notifications), someone has to have Dashboard → Approvals open. A device can ask for at most 300 approvals an hour, and an organization can have 200 waiting at once.
- Invitations are links you share yourself; Verfy sends no email of its own (Supabase Auth sends sign-up and reset emails).
- Policy regexes are checked for nested quantifiers, but regular expressions can still be slow on adversarial input on developer machines.

## Added in 0.30.0

- **Disputes in Verfy Cloud.** Verfy checks that a dispute record is signed, that the receipt inside it is signed by the same key and that its finding matches the receipt. It does not check that the claim is true, and a record signed by a key that is not one of the team's enrolled devices is kept with that said. The arbitrator's link is the only thing that lets them record a verdict: it is 32 random bytes, stored as a hash, limited in time and closed by a verdict or a withdrawal, but anyone the link is forwarded to can use it. The verdict is not signed by a key; its record goes into the team's chained audit log.
- **Approving from Slack** is as strong as the Slack account and the Slack app's signing secret: whoever controls a named approver's Slack account can approve. Organizations that need a passkey for approvals are not affected; Slack cannot approve for them.
- **Email notifications** carry a link to Verfy, never a way to approve. Mail can be read by whoever reads the inbox.
- **Verfy Verified reviewed by a person** is a statement by one person about one version, on the day it was made. It is not an audit, it does not cover later versions, and Verfy is not liable for the server.

## Added in 0.29.0

- **Stop.** `verfy stop` writes `~/.verfy/stop.json`; the rules keep agents from removing it, but anyone at the machine can. A team's stop from Verfy Cloud reaches a device when it next checks: in the background about once a minute while its agents work, and on `verfy sync` or `verfy team stop-check`. A device that is offline, or whose agents are idle, keeps its last answer until then. `verfy resume` and `verfy breakglass` refuse to run without a terminal; the rule that refuses them to agents (VFY-SELF-003) is the real guard, because a program can fake a terminal.
- **Emergency access** is opened by a person at the machine and is meant to let things through. It is recorded, not prevented: each action in the window names it in its receipt, and the window opening and closing are receipts.
- **Observe mode** blocks nothing except what guards Verfy, a stop and protected paths. Turn it on only where you would accept that.
- **Plain-language rules** cover the fixed English forms `verfy rule explain` lists. Other sentences, and other languages, are refused rather than guessed.
- **Rule packs** match tool names by pattern, like the templates: a tool with an unusual name is not covered. They are starting points, not a review of each tool.
- **Personal data** is found by patterns: card numbers with a known prefix that pass the Luhn check, IBANs with valid check digits, the US social security number format, and five or more email addresses at once. Data that is encoded, split, in an image or in another format gets through; a 16-digit ID that happens to pass the Luhn check is asked about.
- **Browser actions** are judged by the element's name or text the tool passes (Playwright, Puppeteer and similar MCP tools). A click by screen position, as computer-use tools do, carries no such text and is not judged.
- **Monthly, merchant and category totals** are kept by the MCP gateway (`spend.json`). Payments that go through a hook alone are checked against per-payment limits only; the SDK keeps its own daily totals (`limits.json`).
- **Time stamps** prove the ledger head existed at the authority's time. Verfy checks the hash, the nonce and the time itself; the authority's signature and certificate chain are checked by OpenSSL when you give it the CA certificates.
- **Disclosure** covers arguments only, and only for receipts written with `receipts.field_hashes` on. The tool name, the time and the verdict are always visible in a receipt.
- **The IETF-draft exports** follow individual drafts (draft-farley-acta-signed-receipts-04, draft-sahu-agent-action-receipts-00) that may change. They are signed again with the same key; they add no proof the Verfy ledger does not have.
- **The Go and Rust verifiers** check signatures, numbering and the chain of `verfy.receipt/1`; disclosures, time stamps, disputes and hand-overs are checked by the Python CLI.
- **Disputes** carry a finding made by fixed rules from the receipt. Verfy has no arbitration or insurance partner, so it decides nothing about who pays and refunds nothing.
- **Agent keys** are files on disk, like the main key. A revocation is a signed file you hand to whoever checks the receipts; there is no online revocation list.
- **Mandates** are checked field by field (amount, currency, payee, expiry). Signatures inside AP2 mandates and x402 payments belong to the payment network and are not checked.
- **Evidence packs** say where Verfy's evidence fits a control; the auditor decides what satisfies it.

## What we do not do

No language model takes part in verdicts or verification. No "100% secure", "hacker-proof" or "guaranteed" claims. No certification, insurance or guarantee products exist in this release.
